# MTEC 3501 — Formative Repository Review

**Audience:** Instructor  
**Use:** Review a student's project repository at a course checkpoint  
**Format:** Repository walkthrough and formative feedback  
**Suggested time:** 10–15 minutes per student

## Purpose

Review whether a visitor to the student's repository can understand the project and find the evidence needed to evaluate its development at the current course stage. This is a formative review of the repository as a project record—not an expectation of perfection, a grade, or a check that every template folder is populated.

Assess what the repository makes visible against assignments introduced by the review date. Do not assess work that is not yet due. In particular, this review does not require a written response to oral presentation feedback. Do not require a completed PoC or a settled technology stack unless the applicable assignment explicitly requires those items.

## Review principles

1. **Start with the visitor's experience.** Can someone unfamiliar with the project understand it and locate relevant evidence without needing undocumented explanation?
2. **Assess discoverability and usefulness, not polish.** A working link to a clear external document may be more useful than a polished but unlinked file.
3. **Follow the repository's organization.** Accept equivalent, sensible locations; do not require every template folder to contain files.
4. **Look for meaningful activity, not volume.** Commit counts, file counts, and numbers of Issues or citations are not measures of quality by themselves.
5. **Use the course timeline.** Evaluate only requirements introduced and due by the selected checkpoint. Mark later work **Not yet due**, not missing.
6. **Verify access before judging absence.** If an external link or private resource cannot be opened, record **Unable to verify** and ask the student to provide access.
7. **Describe repository evidence, not student intent.** “Not findable” means the reviewer could not locate the evidence; it does not prove that the student did not do the work elsewhere.

## Suggested walkthrough

1. Open the repository README and summarize the project in your own words.
2. Follow its links to the project proposal, development record, research, presentation materials, and any relevant GitHub planning tools.
3. Check a sample of the repository's commits or document history for evidence that project work has developed over time.
4. Record what was easy to find, what took effort, and what could not be verified.
5. Give the student one specific strength and one to three useful next actions that would make the project record clearer or more evaluable.

## Review criteria

Apply each criterion only when relevant to the chosen checkpoint. The question throughout is whether a visitor can find enough clear evidence to understand and evaluate the project—not whether every item is complete or polished.

| Criterion | Evidence to look for |
|---|---|
| **1. Repository activity** | Substantive changes over time: project documents revised or added, meaningful commits, Issues updated, or other visible progress. Consider what changed, not just how often changes occurred. |
| **2. README and project description** | A clear current project description, title, and relevant context. The README helps a visitor understand the project and acts as a useful starting point for finding important materials. |
| **3. Organization and navigation** | Project files are in sensible, understandable locations. Important materials are linked or otherwise easy to locate. Empty template folders are not a concern by themselves. |
| **4. Project documentation and development record** | Relevant earlier work—such as speculation, brainstorming, a proposal, or a project log—is available where appropriate and contributes to an understandable record of the project's development. |
| **5. Research** | Research is findable through an accessible Zotero collection link, a repository research document or bibliography, or both, as appropriate to the checkpoint. Sources are identifiable, and any required annotations or synthesis can be located. |
| **6. Presentation and visual materials** | Where required by the checkpoint, slides or equivalent presentation materials, diagrams, or other project visuals are included or linked and accessible. |
| **7. GitHub project management** | Where introduced and required by the checkpoint, relevant Issues, milestones, or a Project board can be found and appear connected to actual project work. |
| **8. Link and content consistency** | Links work; filenames and descriptions are understandable; the README and linked documents describe a reasonably consistent current project. |

## Formative indicators

Use one indicator for each applicable criterion. Do not add indicators into a total or convert them into a grade.

| Indicator | Meaning |
|---|---|
| **2 — Findable and evaluable** | A visitor can locate and understand adequate evidence for this stage of the project. |
| **1 — Present, but difficult to evaluate** | Some evidence exists, but it is incomplete, unclear, hard to locate, or not well connected to the project. |
| **0 — Not findable** | Evidence expected by this checkpoint could not be found in the repository or through its accessible links. Confirm with the student before recording this indicator. |
| **N/A — Not applicable / not yet due** | The criterion does not apply to the project or has not yet been introduced or required. |
| **? — Unable to verify** | A broken link, access restriction, or missing context prevents a fair judgment. |

An indicator of **1** is not automatically a problem requiring extensive revision. Identify the most useful next step rather than turning every weakness into a separate assignment.

## Checkpoint calibration

Before reviewing, note the checkpoint date and assignments in scope. Use the assignment documents to determine whether presentation materials, Zotero organization, GitHub Issues, milestones, or other artifacts are expected by then.

- Earlier checkpoints may focus on project framing, brainstorming, proposal documents, and initial research setup.
- By the Week 6 practice presentation checkpoint, look for the README, practice presentation or equivalent visual material, research evidence (including Zotero/research-document access), and the relevant milestone/Issue work specified for that week.
- Later assignments may add feedback-to-action work, dated roadmaps, technology decisions, practical trials, or PoC evidence. Assess those only when they are in scope and due.
- A review may note an empty or inaccessible research document or a broken README link because it affects discoverability. Describe the issue precisely; do not infer that no research was done.

## Reuse at later checkpoints

This review can be repeated as projects develop. Keep the visitor-centered criteria, but update the assignments in scope and what evidence is expected. Do not retroactively judge students against requirements that were not yet introduced or due.
